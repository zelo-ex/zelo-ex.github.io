* 2.1 应用层协议原理

*这一节是总纲，后面每节都是它的实例。*

** 2.1.1 网络应用的体系结构
+ 应用体系结构：由应用程序研发者设计，规定了如何在各种端系统上组织该应用程序。
+ 客户-服务器体系结构：一个总是打开的服务器主机为多个客户主机提供服务；在该结构，客户相互之间不直接通信。
+ 数据中心：多服务器托管集合，需要供电维护以及大量的费用支撑。
+ P2P 体系结构：应用程序对位于数据中心的专用服务器有最小的（或者没有）依赖，且在对等方之间使用直接通信。
  (P2P = peer to peer 对等方到对等方)
+ 对等方：参与某个 P2P 应用、并与其他对等方（端系统）直接通信的端系统。
  对等方是间歇连接且 IP 地址会变，难以管理。
+ 自扩展性 (self-scalability)：
  每个对等方在请求文件产生工作负载的同时，也在向其他对等方分发文件为系统增加服务能力。

** 2.1.2 进程通信
+ 进程：在主机上运行的应用程序。
  在同一个主机内，使用进程间通信机制通信（由操作系统定义）。
  不同主机，借助传输层提供的服务（由操作系统提供），按照应用协议通过交换报文 (message) 来通信。
+ 客户进程与服务器进程：在一对进程之间的通信会话场景中，
  发起通信的进程标识为客户进程，在会话开始前等待联系的进程标识为服务器进程。
+ 套接字 (socket) 与API：套接字是同一主机内应用进程与运输层协议栈之间的逻辑接口，用于向网络发送数据或从网络接收数据。
  在架构上，套接字的底层实现由操作系统内核（运输层侧）管理，而应用进程（应用层侧）通过开发者编写的代码来调用它；同时，开发者可以通过 API 对运输层的某些行为进行配置。
  在一次网络连接（或通信会话）中，参与通信的两个进程各拥有一个套接字。
  为了在程序中创建和操作这些套接字，操作系统提供了一组标准的编程函数，这组函数被称为套接字API (socket API)。
+ 进程寻址：IP 地址 + 端口号：IP 地址标识主机，端口号标识该主机上的接收进程（更准确地说，标识接收套接字）。
  仅凭 IP 地址不够，因为同一主机上可能同时运行多个进程。
+ 常见应用的熟知端口：Web服务器 -> 80；邮件服务器进程 (SMTP 协议) -> 25。

** 2.1.3 可供应用程序使用的运输服务
+ 可靠数据传输 (reliable data transfer)：保证由应用的一端发送的数据能正确且完整地交付到该应用的另一端。
  丢包容忍度因应用而异：文件传输、Web 文档要求 100% 可靠；音视频可以容忍部分丢失。
  容忍丢失的应用 (loss-tolerant application)：包含多媒体应用，其能够承担一定量的数据丢失。
+ 吞吐量 (throughput)：发送进程向接收进程交付比特的实际速率。（关注点：当前状态，即已经发生的传输）
  可用吞吐量 (available throughput)：在当前网络负载下，发送进程还能额外向接收进程交付比特，且不会引起网络拥塞的速率。（关注点：剩余状态，即路径上剩余的容量潜力）
  具有吞吐量要求的应用程序称为带宽敏感的应用 (bandwidth-sensitive application)，
  而弹性应用程序 (elastic application) 则能根据当前可用带宽尽可能多或少地利用带宽。
+ 定时（时延）：提供定时保证，即要求数据在限定的时间内交付。
  交互式实时应用（网络电话、多人游戏、视频会议）时延过大就“无效”。
+ 安全性：运输协议可以为应用提供安全性服务：机密性（加密，防止报文被中间环节窃听）、数据完整性（防止被篡改）与端点鉴别（确认通信对端身份）。

** 2.1.4 因特网提供的运输服务
+ TCP 服务：面向连接（应用层数据报文流动前，先握手建立连接）、可靠数据传输、拥塞控制（抑制发送进程且试图限制 TCP 连接，使其公平共享网络带宽）。
  TCP 连接 (TCP Connection) 是全双工的，即连接双方的进程可在此连接上同时进行报文收发，且发送报文结束后必须拆除连接。
  不提供定时保证、最小吞吐量保证与加密。
+ UDP 服务：无连接、不可靠数据传输（不保证交付、不保证按序），也不包括拥塞控制机制。
  由于其不提供不必要服务，因此这种轻量级运输协议足够轻量且快，适合容忍丢包或自己在应用层做可靠性的应用。
+ TCP 与 UDP 都不保证的服务（吞吐量、定时）：因特网提供尽力而为的交付，既无法保证最小吞吐量，也无法保证端到端时延上限。
+ TLS (Transport Layer Security，运输层安全)：TLS 是一个建立在 TCP 之上的应用层协议，通过提供增强的套接字 API 为应用层数据提供加密、数据完整性和端点认证，从而防止中间链路的数据被嗅探或篡改。

** 2.1.5 应用层协议
+ 应用层协议：规定不同端系统上的应用进程如何相互交换报文，仅仅作为网络应用的一部分。
  定义了以下内容：报文的类型（如请求/响应）、语法（字段及如何描述）、语义（字段含义），以及进程何时、如何发送报文并对报文做出响应的规则。
+ 公开协议：公开协议由 RFC 文档定义，位于公共域，允许互操作（如 HTTP、SMTP）。
  专用协议：由某个公司自有，有意不为公共域所用（如 Skype、Zoom）。

** 2.1.6 本书涉及的网络应用
+ Web 与 HTTP：Web 页面与 HTTP，含 cookie、Web 缓存、HTTP/2。
+ 电子邮件：SMTP 与邮件访问协议 POP3/IMAP。
+ DNS：因特网的目录服务、资源记录与报文。
+ P2P 文件分发：BitTorrent 与分发时间的计算。
+ 视频流与 CDN：HTTP 流、DASH 与内容分发网。
+ 套接字编程：用 UDP 与 TCP 写网络应用。

** 小测
1. 客户-服务器与 P2P 体系结构各有什么特点？P2P 的“自扩展性”指什么？
   客户-服务器体系结构需要一台一直运行的服务器以进行连接提供服务，而 P2P 体系结构在任意两个对等方间进行连接提供服务；
   P2P 的“自拓展性”是指新对等方的的加入，不仅增加了系统的工作负载，也增加了系统的服务能力。
2. 进程之间通信要经过什么接口？一次通信需要哪两类地址信息？
   经过套接字 API；需要 IP 地址以及端口号。
3. 应用程序可以对运输服务提出哪四个方面的要求？
   可靠传输服务、吞吐量、定时、安全性。
4. TCP 提供哪些服务？UDP 提供哪些服务？两者都不提供什么？
   TCP 提供面向连接服务、可靠传输服务以及拥塞控制机制；
   UDP 提供无连接、不可靠的数据传输服务；两者都不提供吞吐量与定时保证。
5. “网络应用”与“应用层协议”有什么区别？应用层协议通常要规定哪几件事？
   应用层协议只是网络应用的一部分。应用层协议规定报文类型、语法、语义以及进程何时、如何发送报文并对报文做出响应的规则。
6. 能画：应用进程 → 套接字 → 运输层，并说出两端通信用的地址四元组。
   TCP 通信：两端通信使用的地址由 四元组 唯一标识：{ 源 IP 地址, 源端口号, 目的 IP 地址, 目的端口号 }。
   UDP 通信：UDP 报文段首部虽包含源信息，但其套接字仅由 二元组（目的 IP 地址, 目的端口号）唯一标识来进行多路分解。

* 2.2 Web 和 HTTP

*第二章的重头：报文格式与连接方式是后面所有应用层协议的模板。*

** 2.2.1 HTTP 概况
+ HTTP：超文本传输协议 (HyperText Transfer Protocol)，Web 的应用层协议，采用客户-服务器模型。
  定义了 Web 客户向 Web 服务器请求 Web 页面，以及服务器向客户传送 Web 页面的方式。
  HTTP 是一个无状态协议 (stateless protocol)，即 HTTP 服务器在协议层不保存关于客户的任何状态信息。
  原因是简化服务器设计，支持大量并发 TCP 连接；但可以在应用层上进行状态管理，如利用Cookie、Session等机制。
+ 对象与 Web 页面：Web 页面由若干对象组成 (HTML 文件、JPEG 图像、Java 小程序、音视频文件…)。
  多数页面由一个基本 HTML 文件 (base HTML page) 加若干被引用对象构成，每个对象由 URL 寻址。
+ HTTP 客户端与服务器端：Web 浏览器 (Web browser) 实现 HTTP 客户端；Web 服务器 (Web server) 实现 HTTP 服务器端，用于存储 Web 对象，两者通过 HTTP 报文进行交流。
+ HTTP 使用 TCP：客户与服务器先建立 TCP 连接（创建套接字），再在该连接上通过套接字接口发送 HTTP 报文。
  分层结构的优点在于一旦向套接字接口发送报文，该报文就脱离该通信实体控制并进入 TCP 的控制，而不需要关心数据丢失。

** 2.2.2 非持续连接和持续连接
+ 非持续连接：每个对象使用一条单独的 TCP 连接，一条连接上最多发送一个对象，发完即关闭。
+ 持续连接：多个对象共用同一条 TCP 连接，服务器发完响应后不关闭连接，后续请求/响应在同一连接上往返。
  流水线 (pipelining)：不等待未决请求的回答继续发送后续请求。
  HTTP/1.1 默认使用持续连接，并支持流水线；但流水线并非默认必须启用。
+ 非持续连接获取一个对象的时间（2 RTT + 传输时间）：1 个 RTT 用于建立 TCP 连接，1 个 RTT 用于发请求并收到响应的前几个字节，再加大约一个对象的传输时间。
  RTT，即往返时间 (Round-Trip Time)，是指一个短分组从客户端到服务器然后再返回客户所花费的时间，包括分组传播时延、排队时延、分组处理时延等。
+ 并行连接：浏览器常同时打开多条并行 TCP 连接去取被引用对象，以缩短总时间；代价是每条连接都要 OS 开销。

** 2.2.3 HTTP 报文格式
+ 请求报文：请求行 (request line) + 若干首部行 (header line) + 一个空行 + 实体体 (entire body)，示例请求报文如下：
#+BEGIN_SRC text
GET /index.html HTTP/1.1
Host: www.example.com
User-Agent: Mozilla/5.0
Accept: text/html,application/xhtml+xml
Accept-Language: zh-CN,zh;q=0.9
Connection: keep-alive

#+END_SRC
+ 请求行：形如 GET /somedir/page.html HTTP/1.1，包含方法字段、URL 字段和 HTTP 版本字段。
  + GET /index.html HTTP/1.1：请求行，方法为 GET，请求对象是 /index.html，HTTP 版本为 1.1。
+ 请求方法：GET 请求对象；POST 把表单数据放在实体体里提交；HEAD 与 GET 类似，但服务器响应中不包含实体体，只返回状态行和首部行；PUT 把对象上传到指定 URL；DELETE 删除指定对象。
+ 首部行：类似“键值对”的形式。
  + Host: www.example.com：HTTP/1.1 中必需，指明目标主机。
  + User-Agent、Accept、Accept-Language：告诉服务器客户端类型、可接受的内容类型和语言。
  + Connection: keep-alive：希望使用持续连接。
  + 最后有一个空行，表示首部结束。GET 请求一般没有实体体，使用 POST 方法时会使用实体体。
+ 响应报文：状态行 (status line) + 若干首部行 (header line) + 一个空行 + 实体体 (entire body)，示例响应报文如下：
#+BEGIN_SRC text
HTTP/1.1 200 OK
Date: Tue, 15 Oct 2024 12:00:00 GMT
Server: Apache/2.4.41 (Ubuntu)
Last-Modified: Mon, 14 Oct 2024 10:00:00 GMT
Content-Length: 47
Content-Type: text/html; charset=UTF-8
Connection: keep-alive

<html><body><h1>Hello, HTTP!</h1></body></html>
#+END_SRC
+ 状态行：包含协议版本字段、响应码和对应状态信息。
  状态码：200 OK；301 Moved Permanently（对象已永久搬走）；400 Bad Request；404 Not Found；505 HTTP Version Not Supported。
  304 Not Modified 是条件 GET 的应答，见 §2.2.5。
  301 Moved Permanently 通常会带 Location 首部，指示对象的新 URL。
+ 首部行：
  + Date：服务器生成响应的时间。
  + Server：服务器软件信息。
  + Last-Modified：对象最后修改时间。
  + Content-Length: 47：实体主体的字节数为 47（注意不表示报文总长度，因为报文总长度还包括了实体体之外其他所有结构的字节数）。
  + Content-Type: text/html; charset=UTF-8：实体类型是 HTML，字符集为 UTF-8。
  + Connection: keep-alive：保持 TCP 连接，后续请求可继续复用。
    请求中若写 Connection: close，表示希望非持续连接。
  + 空行之后是实体主体，对于响应报文来说是 HTML 内容。
+ 常见首部行：请求常用 Host（对象所在主机）、User-agent、Accept、Connection: close；响应常用 Date、Server、Last-Modified、Content-Length、Content-Type。
+ 实体体：请求报文的实体体用于 POST 提交数据；响应报文的实体体就是被请求的对象本身，是报文的主要部分。
  GET 请求通常没有实体体，HEAD 响应没有实体体。

** 2.2.4 用户与服务器的交互：cookie
+ 为什么需要 cookie：HTTP 服务器是无状态的，但 Web 站点通常希望能够识别用户，于是需要用 cookie 在多次请求之间携带状态以允许站点对用户进行跟踪。
+ Cookie 的典型用途：用户认证、购物车、推荐、会话状态保持。
+ Cookie 是一把双刃剑：方便跟踪用户的同时，也涉及隐私问题。
+ cookie 的四个组件：
  + 响应报文中的 Set-cookie 首部行；
  + 请求报文中的 Cookie 首部行；
  + 用户端浏览器维护的 cookie 文件，并由浏览器自行管理；
  + 位于 Web 站点的后端数据库。
+ 用户会话过程：用户首次访问 Web 站点时，可能需要提供一个用户标识；
  在后续的每次请求中，浏览器会自动在请求报文里带上 Cookie 首部，从而向服务器标识该用户；
  服务器收到 Cookie 首部后，用其中的识别码查后端数据库，从而取出该用户的状态信息。

** 2.2.5 Web 缓存
+ Web 缓存器 (Web cache)：，又称代理服务器 (proxy server)，能代表初始服务器满足 HTTP 请求的网络实体，有自己的磁盘存储空间并存有最近请求过的对象副本。
+ Web 缓存器既是服务器又是客户：当接收浏览器的请求并返回响应报文时作为服务器，当向初始服务器发出请求并接收响应时作为客户。
+ 部署 Web 缓存器的原因：
  1. 减少对客户的响应时间；
  2. 减少一个机构的接入链路到因特网的通信量，从而减少带宽费用；
  3. 从整体上减少因特网上的 Web 流量，从而改善了所有应用的性能。
+ 命中率：由缓存器所满足的请求占全部请求的比率，取决于缓存大小、访问模式、用户群体等。未命中时，缓存器作为客户向初始服务器请求对象，再返回给客户端。
  缓存命中率为 0.4 表示为有 40% 的请求将几乎会由缓存器得到响应，只有剩下的 60% 的请求仍然要由初始服务器来满足。
  （经典题：已知命中率 p 算平均时延）
+ 条件 GET (conditional GET)：代理缓存器 (proxy cache) 在请求首部带上 If-Modified-Since；若副本仍是最新的，服务器返回 304 Not Modified 且不含实体体。
+ 缓存与内容分发网络 (Content Distribution Network, CDN) 的关系：CDN 通过把“缓存/副本”按地理位置分散部署到大量节点上的做法，使大量流量实现了本地化。

** 2.2.6 HTTP/2
+ HTTP/2 目标：减小感知时延。实现手段：经单一 TCP 连接使请求与响应多路复用，提供请求优先次序和服务器推，并提供 HTTP 首部字段的有效压缩。
  不改变 HTTP 方法、状态码、URL 或首部字段，改变数据格式化方法以及客户和服务器之间的传输方式。
+ HTTP/2 多路复用：在单一 TCP 连接上并行交错发送多个请求/响应，避免为每个请求各建一条连接。
+ 二进制分帧：HTTP/2 引入成帧子层，把 HTTP 报文拆成独立的二进制帧，在同一 TCP 连接上交错发送，
  接收端再根据帧头中的流标识符装配。这既是多路复用的实现机制，也是 HTTP/2 的基本传输格式。
+ 首部压缩：使用 HPACK 压缩重复的首部字段，减少传输开销。（Kurose-Ross 教材正文未展开此术语，但可在 RFC 找到）
+ 服务器推送：服务器可以在客户请求 HTML 之前，主动把该页面引用的对象一并推给客户，省掉额外的请求往返。
+ 队头阻塞 (Head Of Line/HOL blocking)：HTTP/2 的多路复用都跑在一条 TCP 连接上，而 TCP 按序交付，一旦某个报文段丢失，后面已到达的数据也只能等重传，于是复用被卡住，这是应用层改不了的队头阻塞。
+ HTTP/3 与 QUIC
  + HTTP/3 = HTTP/2 语义 + QUIC 传输 + QPACK 头部压缩。
  + 每流流量控制：QUIC 在连接级流控之上，为每条流实现独立的流控窗口。
    这能防止单条高速流耗尽整个连接的接收缓冲区，避免流间因资源竞争而相互阻塞，保证了多路复用下的公平性。
  + 低时延连接创建：QUIC 集成了 TLS 1.3，首次连接仅需 1-RTT；对于重复连接，支持 0-RTT，客户端首个数据包即可携带应用数据，极大降低了连接建立延迟。
  + 彻底解决队头阻塞：QUIC 在 UDP 之上实现流感知的多路复用，每条流独立可靠交付（解决问题的根本机制）；
    一条流丢包只阻塞该流自身，其他流不受影响，消除了 HTTP/2 中因 TCP 按序交付导致的传输层队头阻塞。
  + 0-RTT 连接建立：首次连接 1-RTT；对之前连接过的服务器，后续连接支持 0-RTT，第一个数据包即可携带应用数据。
  + 连接迁移：以连接 ID 而非 IP 四元组标识连接，IP 地址变化（如 Wi-Fi 切移动网络）时连接可无缝延续。
  + 头部压缩：使用 QPACK（而非 HTTP/2 的 HPACK），适应 QUIC 的乱序交付，避免头部压缩自身引入队头阻塞。

** 小测
1. HTTP 是无状态协议是什么意思？它和 cookie 是什么关系？
   HTTP 协议本身不保留用户的任何状态；cookie 作为应用层的一个机制，弥补了 HTTP 协议缺乏的状态记录的功能。
2. 非持续连接与持续连接各需要多少 RTT？开销差在哪里？
   非持续连接需要 2N RTT，非流水线的持续连接需要 (n + 1) RTT，带流水线的持续连接需要 2 RTT；
   开销在非持续连接每次传输数据总是需要重新与服务器建立连接，而持续连接仅仅需要建立一次就可以长时间传输数据。
3. 手写一个 HTTP 请求报文和响应报文，指出请求行/状态行、首部、实体体。

   + 首部：L2~L5
   + 无实体体

   + 首部：L2~L6
   + 实体体：L8

4. 状态码 200、301、304、404 分别代表什么？
   200 OK: 服务器完成并正确返回了响应（不意味着返回的数据是正确的）；
   301 Moved Permanently: 服务器上的资源已经永久移走，可能携带移动到的新网址；
   304 Not Modified: 服务器上的资源未发生改动，即与缓存器一致；
   404 Not Found: 要寻找的指定路径上的资源不存在。
5. 条件 GET 与 304 是怎么做到“不重复传对象”的？
   缓存器请求首部带上 If-Modified-Since 并发送条件 GET，如果返回的是 304 则不需要继续操作，否则缓存器需要重新获取副本并缓存。
6. Web 缓存为什么能降低时延、减小出口带宽？命中率如何影响平均时延？
   Web 缓存保存了最近请求的资源并用于返回客户端以降低时延；命中时请求不必经过机构出口链路到因特网，因此也减少了出口链路的 Web 流量和带宽消耗；
   命中率越高，意味着越多数据可直接从缓存器返回而无需请求初始服务器，通过减少报文往返次数来减少平均时延。
7. HTTP/2 相比 HTTP/1.1 改了什么？为什么单一连接上仍可能队头阻塞？
   数据格式化方法和客户与服务器之间的传输方式；HTTP/2 的多路复用都跑在一条 TCP 连接上，而 TCP 按序交付；
   一旦某个报文段丢失，后面已到达的数据也只能等重传，于是复用被卡住。

* 2.3 因特网中的电子邮件

** 2.3.1 SMTP
+ 电子邮件系统的三个主要组成部分：
  + 用户代理 (user agent)：阅读、回复、转发、保存和撰写邮件，如 Outlook 等。
  + 邮件服务器 (mail server)：电子邮件体系结构的核心，存邮箱（管理和维护接收到的报文）、维护待发报文队列。
    一个邮件服务器同时运行客户端与服务器端，在向其他邮件服务器发送邮件时表现为 SMTP 的客户，在从其他邮件服务器接收邮件时表现为 SMTP 的服务器。
  + 简单邮件传输协议 (Simple Mail Transfer Protocol, SMTP)：因特网电子邮件中主要的应用层协议，使用 TCP 可靠数据传输服务，在服务器之间传递报文。
+ SMTP 工作流程与端口 25：发件人用户代理把邮件交给发件方邮件服务器 -> 发件方邮件服务器用 SMTP (TCP 25 端口) 把报文送到收件方邮件服务器 -> 邮件进入收件人邮箱。
  SMTP 传输阶段：握手 (handshaking) -> 报文传输 (transfer of messages) -> 关闭连接 (closure)。
+ 邮件无法交付到收件方邮件服务器：在报文队列中保留该报文，每次等待后（一般30min）尝试一次发送过程；几天后仍旧不成功则删除该报文并以电子邮件形式通知发件方。
+ SMTP 使用持续连接：若同一对邮件服务器之间要送多封邮件，可以在同一条 TCP 连接上连续发送。
+ SMTP 只负责“发送/传递”，不能用来取邮件：SMTP 是“推”协议，把邮件从发方推到收方；从服务器邮箱取邮件要用邮件访问协议，如 IMAP、POP3。
+ SMTP 与 HTTP 的对比：两者都使用持续连接；HTTP 主要是拉、SMTP 是推；SMTP 要求报文（含首部）只用 7-bit ASCII，二进制多媒体必须编码，HTTP 没有这个限制。

** 2.3.2 邮件报文格式
+ 报文组成：报文首部 (From:、To:、Subject: 等首部行) + 一个空行 + 报文体（ASCII 格式表示）。
  必须包含一个 From: 首部行和一个 To: 首部行，可包含一个 Subject: 首部行以及其他可选的首部行。
  SMTP 的 MAIL FROM: 和 RCPT TO: 命令与邮件报文首部的 From:、To: 是两回事：前者是 SMTP 传输阶段的命令，后者是报文本身的首部行。
+ 7-bit ASCII 限制：SMTP 规定邮件报文的首部和报文体都必须用 7-bit ASCII，
  即每个字符都必须属于 7-bit ASCII 字符集，因此非 ASCII 内容必须先编码成 ASCII （如使用 base64 编码）才能通过 SMTP 传输。
+ MIME 与多媒体扩展：MIME 通过额外的首部行说明内容类型与编码方式（如 base64），把二进制多媒体数据变成 ASCII 随 SMTP 传送。

** 2.3.3 邮件访问协议
+ 为什么需要邮件访问协议：收件人的用户代理通常不在邮件服务器上，也不常开机，无法一直开着 SMTP 等信，所以要从服务器邮箱“拉”取邮件。
+ POP3（下载并删除 / 下载并保留）：用户代理与邮件服务器之间的拉取协议，两种模式：下载并删除（取走后服务器上不再保留）、下载并保留（取走后服务器上仍保留）。
  POP3 在会话期间是无状态的，服务器不维护跨会话的用户状态，因此不支持在服务器端创建文件夹。
+ IMAP（服务器端保存、文件夹、部分读取）：邮件保存在服务器上，用户代理可以只读取报文的某一部分、可以建立/维护服务器端文件夹，因而能在多设备之间保持一致状态。
+ 基于 Web 的电子邮件 (HTTP)：用户代理就是浏览器，浏览器用 HTTP 与邮件服务器交互（用户发信、取信都走 HTTP）；
  邮件服务器之间传递邮件仍用 SMTP。邮箱在服务器上，因此换台机器也能看到同样的邮件。

** 小测
1. 一封邮件从发件人到收件人要经过哪些服务器与协议？逐步列出来。
   发件人 UA --(SMTP 或 HTTP)--> 发件人邮件服务器 --(SMTP)--> 收件人邮件服务器 --(POP3/IMAP/HTTP)--> 收件人 UA。
2. 为什么用户代理要把邮件“推”给邮件服务器，而取邮件不能用 SMTP？
   SMTP 是推协议，只用于“发送/传递”邮件；从服务器邮箱取邮件需要邮件访问协议（POP3/IMAP/HTTP），因为这是“拉”操作。
3. SMTP 与 HTTP 有哪些关键区别？
   SMTP 是推协议，HTTP 主要是拉协议；两者都使用持续连接；SMTP 要求报文（含首部）只用 7-bit ASCII，二进制多媒体必须编码成 ASCII 才能传输，HTTP 没有这个限制。
4. 邮件正文为什么只能用 7-bit ASCII？MIME 怎么解决这个问题？
   SMTP 设计时只支持 7-bit ASCII，以保证在早期系统间的兼容性和可靠传输。
   MIME 通过额外的首部行说明内容类型和编码方式，并用 base64 或 quoted-printable 把二进制/非 ASCII 数据编码成 ASCII 字符，随 SMTP 传输。
5. POP3 与 IMAP 的区别？各自适合什么场景？
   POP3 在会话期间无状态，不支持服务器端文件夹，适合用户只在一台机器上读邮件、不需要跨设备同步的场景；
   IMAP 有状态，邮件保存在服务器上，支持文件夹和部分读取，适合多设备访问、需要在服务器端保持一致的场景。

+ SMTP 流程题与“发送/取信各用什么协议”的判断题。
+ 邮件报文首部与格式题。
+ 与 HTTP 对比的概念题。

* 2.4 DNS：因特网的目录服务

** 2.4.1 DNS 提供的服务
+ 域名系统 (Domain Name System, DNS)：因特网的目录服务，是一个由分层的 DNS 服务器实现的分布式数据库，同时也是让主机能查询该分布式数据库的应用层协议。
  与 Web 应用等不同的地方在于，DNS 不是一个和用户直接打交道的应用，而是为因特网上的用户应用程序以及其他软件提供一种把主机名转换为 IP 地址的核心功能。
  DNS 通常采用位于网络边缘的客户和服务器，且由其他应用层协议所使用。
+ DNS 协议：DNS 协议是应用层协议，因为其使用客户-服务器模式运行在通信的端系统之间，在通信的端系统之间通过下面的端到端运输协议来传送 DNS 报文。
  DNS 报文主要通过 UDP 传输，端口 53；当响应报文过大或进行区域传送时，也会使用 TCP。
+ 主机名到 IP 地址的转换（DNS 的主要任务）：在 DNS 服务器把人可读的主机名（如 www.someschool.edu）解析成 IP 地址。
+ 主机别名 (host aliasing) 与规范主机名 (canonical hostname)：主机可以有一个或多个别名，DNS 能返回主机别名对应的规范主机名。
+ 邮件服务器别名 (mail server aliasing)：让公司的邮件服务器用简单别名（如 someschool.edu）被访问。
  MX 记录给出主机别名对应的邮件服务器的规范主机名，客户端再通过 A 记录解析该主机名的 IP 地址。
+ 负载分配 (load distribution)：同一个主机名可以对应一组 IP 地址，DNS 在每个响应中轮转这些地址的顺序，
  客户端通常向排在最前的 IP 发起请求，从而把负载分散到多台复制的服务器上。
+ DNS 的实现：DNS 服务器通常是运行 BIND (Berkeley Internet Name Domain) 软件的 UNIX 机器。
+ DNS 的脆弱性：DNS 协议本身缺乏认证机制，主要面临以下威胁：
  + 分布式拒绝服务 (DDoS) 带宽洪泛攻击：试图向每个 DNS 服务器发送大量的分组，使得大多数合法 DNS 请求得不到应答；
    针对根服务器的 DDoS 攻击因本地 DNS 缓存和流量过滤而难以成功；但 DNS 基础设施的其他部分仍可能成为攻击目标。
  + DNS 投毒攻击：向一台 DNS 服务器发送伪造的回答，诱使服务器在其缓存中接收伪造记录。
  + 中间人攻击：拦截查询并返回伪造应答。
  + DNSSEC 是 DNS 的安全扩展，通过数字签名保证 DNS 数据的真实性与完整性。

** 2.4.2 DNS 工作机理概述
+ 为什么不能只用一台集中式 DNS 服务器：
  1. 单点故障 (single point of failure)：单台服务器故障会导致整个因特网崩溃；
  2. 通信容量 (traffic volume)：单个服务器要处理所有的 DNS 查询；
  3. 远距离的集中式数据库 (distant centralized database)：远距离的查询可能需要经过低速和拥塞的链路，造成很大的时延；
  4. 维护 (maintenance)：会使 DNS 服务器的数据库变得无比庞大，且不得不为解决新主机的添加而导致频繁更新。
+ 根 DNS 服务器：DNS 层次的最顶层，收到查询后返回相应 TLD 服务器的 IP 地址。
  全球共有 13 个根服务器，由 12 个不同组织管理，每个都有多个副本分布在世界各地。
+ 顶级域 (Top-Level Domain, TLD) DNS 服务器：负责 com、org、net、edu、gov 以及国家顶级域等，返回对应权威 DNS 服务器的 IP 地址；支持 TLD 的网络基础设施可能是大而复杂的。
+ 权威 DNS 服务器：由组织自己实现并维护，或付费存储在某服务提供商的权威 DNS 服务器，用于保存该组织主机名到 IP 的权威记录。
+ 本地 DNS 服务器 (local DNS server)：不严格属于 DNS 层次，起代理作用；通常由 ISP 或单位提供，是主机配置中的默认名字服务器。
+ 递归查询 (recursive query) 与迭代查询 (iterative query)：递归 = 被查者替你查到底并返回结果；迭代 = 被查者只告诉“下一个该问谁”。
  常见链路：主机 → 本地 DNS（递归查询）→ 根 → TLD → 权威（后三步通常是迭代查询）。
+ DNS 缓存 (DNS caching)：DNS 服务器把查询到的记录缓存起来，TTL (Time To Live，生存时间) 到期后删除；缓存能改善时延性能并减少在因特网上到处传输的 DNS 报文数量。
  本地 DNS 服务器不仅缓存最终结果，也会缓存 TLD 和权威服务器的 IP 地址。

** 2.4.3 DNS 记录和报文
+ 资源记录的四元组：形如 (Name, Value, Type, TTL)，TTL 决定记录何时从缓存中删除。
  + A 记录：Name = 主机名，Value = 该主机的 IP 地址，最常用的记录类型。
  + NS 记录：Name = 主机所在域（如 foo.com），Value = 该域的权威 DNS 服务器的主机名。
  + CNAME 记录：Name = 别名，Value = 对应的规范主机名。
  + MX 记录：Name = 邮件服务器的别名，Value = 该邮件服务器的规范主机名。
    通过 MX 记录，一个公司的邮件服务器和其他服务器可以使用相同的别名；通过请求 CNAME 记录或 MX 记录区分其他服务器和邮件服务器。
+ DNS 报文：查询报文与应答报文格式相同，由首部区域 (12 Byte) + 问题区域 + 回答区域 + 权威区域 + 附加区域组成。
  + 首部区域：16bit 的标识符字段，用于标识该查询；标志字段含有若干标识；还包含了后四个数据区域的有关数量的字段。
    + 1bit 的“查询/回答”标志位指出是查询报文 “0” 还是回答报文 “1”；
    + 1bit 的“权威的”标志位指出该 DNS 服务器是对应的权威 DNS 服务器；
    + 1bit 的“希望递归”标志位指出该 DNS 服务器希望递归查询；
    + 1bit 的“递归可用”标志位指出该 DNS 服务器支持递归查询；
    + ...
  + 问题区域：包含了正在进行的查询信息，包括名字字段（包含正在被查询的主机名字）和类型字段（指出有关该名字正被询问的问题类型，如类型 MX 或者类型 A）。
  + 回答区域：包含了最初请求的名字的资源记录，可以包含多条 RR，因此一个主机名可以有多个 IP 地址。
  + 权威区域：包含了其他权威服务器的记录。
  + 附加区域：包含了其他有帮助的记录。
+ nslookup 与 dig：命令行 DNS 查询工具；nslookup 是书中使用的工具，可指定查询的 DNS 服务器与记录类型 (dig 是同类工具，输出更详细)。
+ 注册登记机构 (registrar)：一个商业实体，验证域名的唯一性并将该域名输入 DNS 数据库，且对提供的服务收取少量费用。
  因特网名字和地址分配机构 (Internet Corporation for Assigned Names and Numbers, ICANN) 向各种注册登记机构授权。
+ 注册域名：向注册登记机构提供域名的基本、辅助权威 DNS 服务器的名字和 IP 地址，
  对每一个权威 DNS 服务器，该注册登记机构确保将一个类型 NS 和一个类型 A 的记录输入 TLD 服务器，
  还必须确保用于 Web 服务器的类型 A 资源记录和用于邮件服务器的类型 MX 资源记录被输入到权威 DNS 服务器中。
+ 访问域名：主机向本地 DNS 服务器发起查询；本地 DNS 依次查询根、TLD、权威 DNS 服务器（通常为迭代查询），最终获得目标主机 IP；
  主机再用该 IP 建立 TCP 连接。若本地 DNS 有缓存，可跳过部分步骤。

** 小测
1. DNS 除了把主机名解析成 IP 地址，还提供哪些服务？
   主机别名、邮件服务器别名、负载分配。
2. 画出访问某网站时 DNS 的完整查询链（本地 → 根 → TLD → 权威），并指出哪几步是递归、哪几步是迭代。
   主机 → 本地 DNS（递归查询）→ 根 → TLD → 权威（后三步通常是迭代查询）。
3. 为什么需要 DNS 缓存？缓存会带来什么问题？
   缓存能改善时延性能并减少在因特网上到处传输的 DNS 报文数量；缓存可能被攻击者利用，例如 DNS 缓存投毒攻击。
4. 资源记录的四元组分别是什么？给 A、NS、CNAME、MX 各举一个例子。
   (Name, Value, Type, TTL)；
   (relay1.bar.foo.com, 145.37.93.126, A)；
   (foo.com, dns.foo.com, NS)；
   (foo.com, relay1.bar.foo.com, CNAME)；
   (foo.com, mail.bar.foo.com, MX)。
5. 一次 DNS 解析的时延由哪几段 RTT 组成？
   主机和本地 DNS，本地 DNS 和根服务器，本地 DNS 和 TLD 服务器，本地 DNS 和权威 DNS 服务器。
6. 能算：给定各级服务器的往返时间，算出解析一个名字的总时延。
   设主机到本地 DNS 的往返时间为 \(RTT_0\)，本地 DNS 到根的为 \(RTT_1\)，本地 DNS 到 TLD 的为 \(RTT_2\)，本地 DNS 到权威 DNS 的为 \(RTT_3\)，
   则总时延为\(T \approx RTT_0 + RTT_1 + RTT_2 + RTT_3\)。若各级 RTT 相等，均为 \(1RTT\)，则 \(T \approx 4RTT\)。

** 对应习题类型
+ DNS 查询过程题（画查询链、判断递归/迭代）。
+ 资源记录类型匹配题。
+ DNS 解析时延计算题。

* 2.5 P2P 应用

** 2.5.1 P2P 文件分发
+ P2P 文件分发与 BitTorrent：每个对等方既下载也上传，因此分发时间不随对等方数量线性增长（对照 §2.1.1 的自扩展性）。
  分发时间 (distribution time)：所有 N 个对等方得到该文件的副本所需要的时间；对于 P2P 体系结构，最小分发时间总是小于客户-服务器体系结构的分发时间。
+ 洪流 (torrent) 与块 (chunk)：文件被切成等长的块；参与同一文件分发的所有对等方构成一个洪流，对等方加入后从其他对等方那里取块。
+ 追踪器 (tracker) 与邻近对等方：追踪器登记加入洪流的对等方，新加入者从它那里拿到对等方列表，然后与其中一些建立 TCP 连接，成为彼此的邻近对等方。
  随着时间流逝，一些邻近对等方可能离开，其他新的的对等方可能试图和该对等方创建 TCP 连接，因此一个对等方的邻近对等方将随着时间而波动。
+ 最稀有优先 (rarest first)：优先请求“在邻近对等方中副本最少”的块，使稀有块尽快扩散，其目标是（大致地）均衡每个块在洪流中的副本数量。
+ 对等方的加入与离开、自扩展性：对等方随时加入或离开，但由于每个新对等方都带来上载能力，分发时间增长得比客户-服务器慢。
+ 搭便车与“一报还一报” (tit-for-tat)：为避免只下载不上传，对等方优先给“当前能给它最大速率”的对等方发送块，并周期性试送新对等方（乐观疏通）。

** 必会公式

| 名称                | 公式                                                 | 说明                                                       |
|---------------------+------------------------------------------------------+------------------------------------------------------------|
| 客户-服务器分发时间 | \(D_{cs} = \max\{ NF/u_s,\ F/d_{min} \}\)                  | N 个对等方、文件 F bit、服务器上载 u_s、最慢下载速率 d_min |
| P2P 分发时间        | \(D_{p2p} = \max\{ F/u_s,\ F/d_{min},\ NF/(u_s+\sum u_i) \}\) | 分母中 \(\sum u_i\) 是全部对等方上载速率之和                  |

** 小测
1. 为什么 P2P 的分发时间随对等方数量增长得比客户-服务器慢得多？
   每个对等方不仅下载，还贡献上载带宽，使总上载能力随对等方数量增加而增加，因此分发时间增长得比客户-服务器慢得多。
2. 写出客户-服务器与 P2P 的分发时间公式，并逐项说明含义。
   见上述“必会公式”。
3. 什么条件下 P2P 的分发时间由服务器上载速率决定？
   当对等方的总上载带宽\(\sum{u_i}>(N-1)u_s\)时，\(\frac{F}{u_s}\)成为最大项，P2P 分发时间由服务器上载速率决定。
4. BitTorrent 的“最稀有优先”和“一报还一报”分别解决什么问题？
   最稀有优先：优先请求副本最少的块，使稀有块尽快扩散，均衡各块的副本数量；
   一报还一报：避免对等方只下载不上传。
5. 能算：给定 F、N、u_s、u_i，分别算出两种方式的分发时间并比较。
   \(D_{cs} = \max\left\{ \frac{NF}{u_s},\ \frac{F}{d_{\min}} \right\}\)
   \(D_{p2p} = \max\left\{ \frac{F}{u_s},\ \frac{F}{d_{\min}},\ \frac{NF}{u_s+\sum_{i=1}^{N}u_i} \right\}\)
   

** 对应习题类型
+ 分发时间计算与比较题（常考：给参数算 D_cs 与 D_p2p）。
+ BitTorrent 机制的概念题。

* 2.6 视频流和内容分发网

*2.6.4 案例学习第一遍可以略读。*

** 2.6.1 因特网视频
+ 视频的比特率与压缩编码：视频是逐帧图像序列，可用压缩（如 H.264）把所需比特率大幅降低；比特率越高，画质越好。
+ 流式视频 (streaming stored video)：预先录制好、存在服务器上的视频，用户随时点播（区别于实时视频会议那种边采边传）。
+ 连续播放与缓冲：客户端一边接收一边播放，接收速率会波动，因此要靠客户端缓冲 (playout buffer) 吸收时延抖动。

** 2.6.2 HTTP 流和 DASH
+ HTTP 流：视频以 HTTP 字节流的方式传输，客户端边收边播。
  主流视频系统都用 HTTP，因为 HTTP/CDN 已就绪，且 HTTP 报文容易穿过防火墙与 NAT。
+ HTTP 流的一个局限是：服务器对所有客户端发送相同编码的视频，无法根据每个客户端的带宽自适应；DASH 通过多码率版本和客户端逐块选择解决了这个问题。
+ 字节范围请求：HTTP 提供 Range 首部，客户端可以只请求文件的某一段字节（按块取数据的基础）。
+ 客户端缓冲与播放时延：客户端先缓存若干秒再开始播放，用一点启动延迟换取对带宽波动与抖动的缓冲。
+ DASH (Dynamic Adaptive Streaming over HTTP，基于 HTTP 的动态自适应流)：服务器把视频切成块，每块存成多个不同码率的版本；客户端根据当前带宽与缓冲状况，逐块选择码率。
+ 码率版本与自适应切换：客户端周期估计服务器到自己的带宽，按 manifest 文件给出的各版本 URL 选择可持续的最高码率。

** 2.6.3 内容分发网
+ 单一巨型数据中心的问题（突发流量、单点故障、带宽、时延）：单点故障；网络拥塞点；到远处用户的路径长且可能拥塞；突发流量下无法扩展。
+ CDN 的基本思想（把内容复制到多个站点）：把内容副本存放到多个地理分散的站点，用户从较近/状况较好的节点取内容。
+ 深入部署 (enter deep) 与邀请做客 (bring home)：enter deep = 把服务器深入部署到许多接入网中（离用户近，如 Akamai）；bring home = 只在接入网附近的 PoP 部署较少的大集群（如 Limelight），运维成本低但离用户稍远。
+ 内容选择与集群选择策略：内容选择 = 决定把哪些内容/哪些版本放到哪些节点；集群选择 = 决定把哪个集群分配给某个用户（地理最近、实时测量）。
+ CDN 与 ISP 的对等互联：CDN 通过与 ISP 对等互联 (peering) 把内容送到用户附近，降低时延与传输成本。

** 2.6.4 案例学习：Netflix、YouTube 和 Kankan
+ Netflix（公有云 + 私有 CDN）：注册、计费、推荐等在公有云 (AWS) 上做，视频文件存在自建的 Open Connect CDN 里；用 DASH 做自适应码率。
+ YouTube (Google 数据中心与 CDN)：依托 Google 自有的数据中心与 CDN 分发视频，视频分块、多码率存储，客户端自适应选择。

** 小测
1. 为什么流式视频几乎都走 HTTP，而不用 UDP？
   HTTP/CDN 已就绪，且 HTTP 报文容易穿过防火墙与 NAT。
2. DASH 的“自适应”指什么？客户端依据什么切换码率？
   服务器把视频切成块并存成多个不同码率的版本，由客户端逐块选择码率；当前带宽与缓冲状况。
3. 单一巨型数据中心在突发流量、单点故障、带宽与时延上各有什么问题？
   单点故障；网络拥塞点；到远处用户的路径长且可能拥塞；突发流量下无法扩展。
4. “深入部署”和“邀请做客”各有什么优缺点？
   “深入部署”优点在靠近端用户，改善用户感受的时延和吞吐量；缺点是维护和管理集群困难。
   “邀请做客”有点在通常仅产生较低的维护和管理开销；缺点是对端用户有较高时延和较低吞吐量。
5. Netflix 与 YouTube 的架构有什么相同点和不同点？
   相同点：两者都使用专用 CDN 分发视频。
   不同点：Netflix 使用自建 Open Connect CDN + DASH 自适应流，不使用拉高速缓存和 CDN 重定向；
   YouTube 使用 Google 自有 CDN，采用非自适应的HTTP流，码率选择依赖用户手动操作，依赖拉高速缓存和 CDN 重定向。
6. CDN 是怎么选择为用户服务的集群的？
   地理上最为邻近；实时测量。

** 对应习题类型
+ 概念题为主：CDN 部署方式、内容选择策略、DASH 与 HTTP 流。
+ 可能结合 2.2 问“用什么协议传输、为什么”。

* 2.7 套接字编程：生成网络应用

*动手节：两个程序都要真的跑通，可以放到最后做。*

** 2.7.1 UDP 套接字编程
+ UDP 套接字：无连接、不保证交付：发送前不做握手；发送方必须为每个报文显式附上目的 IP 与端口；报文可能丢失、也可能乱序到达。
+ 客户端流程（创建套接字 → sendto → recvfrom）：创建 UDP 套接字 → sendto（目的地址、端口、报文）→ recvfrom 读回响应 → 关闭套接字。
+ 服务器流程（绑定端口 → recvfrom → sendto）：创建套接字并 bind 到已知端口 → 循环 recvfrom 收报文（从报文中得到发送方的地址与端口）→ 用 sendto 回送响应。
+ 应用层要自己负责的可靠性：UDP 不保证交付与顺序，如果应用需要可靠传输，丢包检测、重传、排序都得在应用层自己做。

** 2.7.2 TCP 套接字编程
+ TCP 套接字：面向连接、字节流：双方必须先建立 TCP 连接（三次握手），数据被当作连续的字节流，TCP 保证按序、可靠交付。
+ 欢迎套接字与连接套接字：服务器有一个“欢迎套接字”（固定在已知端口上等待连接请求）；每当 accept 一个客户，就会（由 OS 隐式地）新建一个“连接套接字”，专门与这个客户通信。
+ 三次握手与服务器并发处理：客户发起连接时完成三次握手；服务器通常为每个客户创建一个进程/线程，从而并发服务多个客户。
+ 客户端/服务器的循环 (read/write、close)：客户端建连后读写数据并在结束时关闭；服务器 accept 得到连接套接字后读写数据，而欢迎套接字继续等待新的客户连接。

** 小测
1. UDP 与 TCP 在服务器端的主要差别是什么（需要几个套接字）？
   UDP 服务器：1 个套接字，既收又发。
   TCP 服务器：2 个套接字——欢迎套接字负责 accept，连接套接字负责与每个客户通信。
2. 为什么 TCP 服务器要为每个客户建立新连接？欢迎套接字起什么作用？
   欢迎套接字固定在已知端口上等待连接请求，本身不传输数据。
   每 accept 一个客户，就新建一个连接套接字，专门服务这个客户；这样欢迎套接字可以继续等待其他客户，实现并发服务。
3. UDP 程序里，报文要携带什么信息服务器才能回送？
   服务器不需要报文里携带额外信息。recvfrom 会同时返回发送方的 IP 和端口（clientAddress），服务器用这个地址 sendto 回送即可。
4. 要实现“文件传输”程序，选 UDP 还是 TCP？为什么？
   选 TCP。文件传输要求数据不丢失、不乱序、完整到达；TCP 提供可靠、按序的字节流传输。UDP 不保证交付和顺序，要在应用层自己做丢包检测、重传、排序，代价大。
5. 能写：把 UDP 回显程序和它的 TCP 版本都跑通。

* 第二章公式速查卡

#+BEGIN_SRC text
非持续连接单个对象 ≈ 2 RTT + 对象传输时间
非持续连接 N 个对象 ≈ N * (2 RTT + 对象传输时间)
持续连接 ≈ 2 RTT（建连 + 首对象）+ (N - 1) * (RTT + 对象传输时间)
Web 缓存平均时延 ≈ p * 局域网时延 + (1 - p) * (局域网时延 + 互联网时延)
客户-服务器分发时间 D_cs = max(N * F / u_s, F / d_min)
P2P 分发时间 D_p2p = max(F / u_s, F / d_min, N * F / (u_s + Σ u_i))
DNS 解析时延 ≈ 查询链上各段 RTT 之和（命中缓存则接近 0）
#+END_SRC

单位坑：

+ 文件大小 F 常给 Byte，速率常给 Mbps，先 ×8 统一到 bit。
+ RTT 与传输时间是两回事：RTT 是往返时延，传输时间 = L/R。
+ P2P 里 u_s 是服务器上载速率，u_i 是对等方上载速率，d_min 是最慢下载者的下载速率。
+ 公式里的 N 是同时下载的对等方数量，不是总用户数。
+ DNS 的 TTL、HTTP 的 Cache-Control 单位是秒，不要当成 RTT。
